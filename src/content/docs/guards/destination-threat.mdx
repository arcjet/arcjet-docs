Protect scores the **caller** of an HTTP request. A Guard policy can score the
**hosts a call would contact** – a WebFetch URL, an absolute URL inside a shell
command – with Arcjet threat intel. The lookup runs only when a published
policy declares an Arcjet threat intel detector. Rego stays pure: it reads a
bounded verdict under `input.signals.ip_threat`, keyed by the detector ID you
declared.

For inbound client IP analysis on `protect()`, see
<Link.Page href="/ip-threat-intelligence">IP threat intelligence</Link.Page>.

## Declare the detector

Give the detector an ID, name a `SERVER` string or string list of hosts, and
choose the Arcjet threat intel (IP threat) kind. It takes no configuration.

| Field | Value |
| --- | --- |
| Kind | IP threat (`GUARD_POLICY_DETECTOR_KIND_IP_THREAT`) |
| Input exposure | `SERVER` |
| Input kind | `STRING` or `STRING_LIST` |
| Signals group | `input.signals.ip_threat.<detector_id>` |

An empty list is risk `none`. Private, loopback, link-local, CGNAT, multicast,
and unspecified addresses are not scored. More than eight public destinations
fails closed: scoring a prefix and still deciding would allow a malicious host
past the cut.

A coding agent hook fills `destinations` for you. An application Guard call
maps the hosts it is about to contact into a declared input of the same shape.

## Read the verdict in Rego

The rolled-up fields are worst-wins across every public host that completed
scoring:

| Field | Meaning |
| --- | --- |
| `detected` | `true` when `risk_level` is `high` or `critical` |
| `risk_level` | `none`, `low`, `medium`, `high`, or `critical` |
| `reputation` | Upstream label such as `malicious`, `suspicious`, or `unknown` |
| `activities` | Observed behaviors for the worst host |
| `host` | Host that produced the worst assessment. Empty when risk is `none` |
| `ip` | Address looked up for that host |
| `assessments` | One entry per public destination that completed scoring, in input order |

Name the set of risk levels you deny. A comparison with `>= "high"` is wrong:
`critical` sorts before `high`, and `none` sorts after it.

```rego
package arcjet.guard

import rego.v1

deny contains "malicious-destination" if {
	input.signals.ip_threat.dest.risk_level in {"high", "critical"}
}
```

`assessments` is on the same signal object Rego and Activity read. Each entry
carries `host`, `ip`, `risk_level`, `reputation`, `activities`, and `detected`.
A host whose lookup failed is omitted: the detector either fails closed or
already has a high or critical peer that decides the call.

## Sample policy for destination threat

The Console offers `coding-agent.destination-threat` as a starter. Attach it to
**Tool call**. It declares `tool_kind` and `destinations`, runs detector ID
`dest` over `destinations`, and denies when risk is high or critical for any
tool kind.

`destinations` holds the hosts of the tool's URL arguments, plus the hosts of
absolute URLs inside a shell command. A `curl` in Bash is covered. An allowlist
that only checks `tool_kind == "web"` is not.

```rego
deny contains "malicious-destination" if {
	input.signals.ip_threat.dest.risk_level in {"high", "critical"}
}
```

| Situation | Expected |
| --- | --- |
| Empty `destinations` | Allowed (risk `none`) |
| Unlisted host such as `docs.arcjet.com` | Allowed (risk `none`) |
| Low risk | Allowed |
| High or critical risk | Denied (`malicious-destination`) |

### Optional: test with a demo host

For live demos of this starter, `evil.arcjet.com` and its subdomains (for
example `https://www.evil.arcjet.com/...`) always score high without a DNS or
IP database lookup. Use that host in a tool call or shell command when the
policy is enabled.

Do not attach this policy to **Prompt**. `destinations` is empty when a prompt
is submitted, so a live detector rule with nothing to score fails closed and
denies every prompt.

For the full coding agent contract and the other starters, see
<Link.Page href="/coding-agents/policies">Coding agent policies</Link.Page>.

## Create an outbound allowlist

An allowlist and destination threat answer different questions:

| Control | Question it answers |
| --- | --- |
| Domain allowlist | Is this host on the list we reviewed? |
| Destination threat | Does Arcjet threat intel mark this host high or critical risk? |

Write an allowlist **into** the policy, never as an input the agent supplies. A
list the agent sent is a list the agent could widen.

The starters below are single-concern policies. If a reviewed host must
**bypass** destination threat, do not publish them beside each other – see
[Combine allowlist and threat](#combine-allowlist-and-threat).

### Domain allowlist for web fetches

The starter `coding-agent.egress-allowlist` compares `domains` – the hosts of
URL arguments – against a set you edit in Rego. It scopes to
`tool_kind == "web"`, so a shell command that embeds a URL does not hit this
rule.

```rego
deny contains "unlisted-domain" if {
	input.values.tool_kind == "web"
	some host in input.values.domains
	not host in {"docs.arcjet.com", "github.com", "raw.githubusercontent.com"}
}
```

Replace the set with the hosts your organization has reviewed before the rule
goes live.

### MCP server allowlist

The starter `coding-agent.mcp-allowlist` uses the same pattern for MCP servers:

```rego
deny contains "unlisted-mcp-server" if {
	input.values.tool_kind == "mcp"
	not input.values.mcp_server in {"arcjet", "github", "sentry"}
}
```

### Combine allowlist and threat

The point of an allowlist next to destination threat is that a **reviewed host
bypasses** the threat deny. That shape needs **one** policy. The Console
starters `coding-agent.egress-allowlist` and
`coding-agent.destination-threat` cannot express it: each is a separate row
with its own deny rule, and neither short-circuits the other.

<Aside type="caution" title="Do not publish both starters for allowlist exceptions">
  Arcjet runs every LIVE policy attached to **Tool call** and applies the most
  restrictive decision. If you publish both starters, a host on the allowlist
  that scores high or critical is still denied by destination threat. The
  allowlist does not carve out an exception. Use one custom policy instead.
</Aside>

Write both checks in the same Rego body. Deny unreviewed hosts on web tools.
Deny high or critical threat only for hosts that are **not** on the allowlist –
so an allowlisted host is allowed even when threat intel scores it high or
critical:

```rego
allowed := {"docs.arcjet.com", "github.com", "raw.githubusercontent.com"}

deny contains "unlisted-domain" if {
	input.values.tool_kind == "web"
	some host in input.values.domains
	not host in allowed
}

deny contains "malicious-destination" if {
	some a in input.signals.ip_threat.dest.assessments
	a.risk_level in {"high", "critical"}
	not a.host in allowed
}
```

Declare the Arcjet threat intel detector with ID `dest` over `destinations`,
the same inputs the destination-threat starter uses, plus `tool_kind` and
`domains` for the allowlist rule. Attach the policy to **Tool call**.

| Situation | Expected |
| --- | --- |
| Web fetch to an unlisted host | Denied (`unlisted-domain`) |
| Allowlisted host, high or critical risk | Allowed (threat deny skipped) |
| Unlisted host, high or critical risk | Denied (`malicious-destination`) |
| Shell `curl` to a high-risk host not on the allowlist | Denied (`malicious-destination`) |

Publish the two starters only when you want **both** constraints with no
exception – every host must be allowlisted **and** must not be high or
critical risk. That is not allowlist-bypass-of-threat.

For application Guard calls, map hosts into a `SERVER` string list, declare an
Arcjet threat intel detector over that input, and hardcode the allow set in
Rego or pass a trusted `allowed_domains` list from application configuration –
not from the model. Keep the bypass in the same policy as the threat rule.

## Fail closed behavior

| Condition | Result |
| --- | --- |
| Host missing from the threat database | Risk `none` |
| Lookup or DNS resolution cannot complete | Live rule is incomplete and denies (`AJP1009`) |
| One host already high or critical while another lookup fails | High or critical verdict still returned |
| More than eight public destinations | Fails closed |
| Deployment cannot reach the IP database when a destination is present | Fails closed |

`AJP1009` is the Arcjet threat intel lookup code. Model-backed detector outages
stay `AJP1004`. When both kinds fail on one policy, the expression keeps
`AJP1004` until every failure was a threat intel lookup. For more information,
see <Link.Page href="/guards/errors">Policy error codes</Link.Page>.

The denial reason sent to the agent names rule IDs only.
