The following sections describe how to use Arcjet effectively in your
applications.

## Single client instance

We recommend creating a single instance of the Arcjet client object and reusing
it throughout your application. This is because the SDK caches decisions and
configuration to improve performance. It also means the object is created
outside of the route handler to avoid creating a new instance on every request.

The pattern we recommend is to create a utility file that exports the Arcjet
object and then import it where you need it.

<Tabs syncKey="language">
<TabItem label="JavaScript / TypeScript">

In the JS SDKs, use `withRule` to attach rules specific to each route or
location in your app.

For example, in a Next.js app you might create a file `/lib/arcjet.ts` that
creates and exports the Arcjet instance:

<Code code={ArcjetLib} lang="ts" title="/lib/arcjet.ts" />

Then, in your request handler you can import the Arcjet instance and use
`withRule` to add any route-specific rules. `protect()` can then be called
inside the route handler.

```ts
import arcjet, { detectBot, fixedWindow } from "@/lib/arcjet";

// Add rules to the base Arcjet instance outside of the handler function
const aj = arcjet
  .withRule(
    detectBot({
      mode: "LIVE", // will block requests. Use "DRY_RUN" to log only
      // configured with a list of bots to allow from
      // https://arcjet.com/bot-list
      allow: [], // blocks all automated clients
    }),
  )
  // You can chain multiple rules, so we'll include a rate limit
  .withRule(
    fixedWindow({
      mode: "LIVE",
      max: 100,
      window: "60s",
    }),
  );

export async function GET(req: Request) {
  // The protect method returns a decision object that contains information
  // about the request.
  const decision = await aj.protect(req);

  // ... handle the request
}
```

</TabItem>
<TabItem label="Python">

In the Python SDK, create one base client and add route-specific rules with
`with_rule()`. The clone shares this instance's `DecisionCache`, key,
characteristics, and transport. The original client is unchanged.

Use `arcjet()` for async frameworks (FastAPI, Starlette) and `arcjet_sync()`
for sync frameworks (Flask, Django). HTTP rule factories require `mode`.

<Code code={ArcjetLibPy} lang="py" title="/lib/arcjet.py" />

Then import the client you need inside each route handler and call `protect()`
once per request:

```py
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

from lib.arcjet import aj_read

app = FastAPI()


@app.get("/items")
async def list_items(request: Request):
    decision = await aj_read.protect(request)

    if decision.is_denied():
        return JSONResponse({"error": "Forbidden"}, status_code=403)

    # ... handle the request
```

If you only need one rule set across the whole app, a single client is fine.

## Avoid Arcjet in middleware

We do not recommend using Arcjet in middleware. This is because middleware lacks
the context of the route handler, making it difficult to apply route-specific
rules or customize responses based on the request.

Our recommendation is to call `protect()` in each route handler where you need
it. This offers the most flexibility and lets you customize the behavior for
each route.

## Call `protect()` once per request

Call the Arcjet `protect()` function only once per request.

This is usually only a problem if you use Arcjet both in middleware and in route
handlers. We do not recommend using middleware, but if you are using it then use
a middleware helper to scope the call to Arcjet only to routes that need it.

## Start in dry run mode

We recommend starting each new rule in `DRY_RUN` mode. When configured this way,
each rule returns its decision, but the end conclusion is always `ALLOW`. This
is useful for testing and tuning your rules before switching to `LIVE`.

As these are configured in code, you can use other mechanisms to set the mode.
For example, you could use an existing feature flag system to dynamically
change the rule mode. We have an example showing how to sample traffic between
`DRY_RUN` and `LIVE` modes in the
<Link.Page href="/blueprints/sampling">Sampling traffic blueprint</Link.Page>.

For teams with separate security and engineering owners, keep feature-specific
rules in code so developers can review them with the route or workflow they
protect. Use <Link.Page href="/remote-rules">remote rules</Link.Page> for
operational changes that SecOps needs to test, promote, or roll back against
live traffic without waiting for an application deploy.

:::tip[Using the MCP server]
If you're using the <Link.Page href="/mcp-server">Arcjet MCP server</Link.Page>,
call `get-dry-run-impact` to see exactly how many currently-allowed requests
would be blocked before promoting a dry-run rule to live. You can also create
and promote <Link.Page href="/remote-rules">remote rules</Link.Page> directly
through MCP without code changes.
:::

## Configure proxies and load balancers

Arcjet needs to see the original client IP address to make accurate decisions.
If your application is behind a proxy or load balancer, make sure that Arcjet
can access the original IP address.

Most proxies and load balancers add an `X-Forwarded-For` header to requests that
contains the original client IP address. Make sure that this header reaches your
application and that you configure Arcjet to ignore the proxy IP addresses.

:::caution[Forwarding headers are not proof of origin]
JavaScript and Python integrations may fall back to common forwarding headers
when the framework and hosting platform do not expose a usable client address.
This preserves protection coverage, but a directly connected client may be able
to spoof the value. Arcjet labels that source `unverified-header`, logs the
provenance at debug level, and warns once per client. The Go SDK instead ignores
`X-Forwarded-For` until the direct peer matches `Config.Proxies`.

Do not silence the warning by copying a forwarding header into `ipSrc`,
`ip_src`, or `WithIPSrc`. A manual override is trusted application input. Derive
it only from a framework or infrastructure source whose trust boundary you have
verified.
:::

This is not necessary on platforms such as Firebase, Netlify, Fly.io, or Vercel
because Arcjet can auto-detect the proxy IPs for these platforms.

For other platforms, configure the `proxies` option when creating the Arcjet
instance. For example, if the load balancer is at `203.0.113.100` and the
client IP address is `198.51.100.1`, the `X-Forwarded-For` header is:

```http
X-Forwarded-For: 198.51.100.1, 203.0.113.100
```

Set the `proxies` field to `["203.0.113.100"]` so Arcjet uses `198.51.100.1` as
the client IP address.

You can also specify CIDR ranges to match multiple IP addresses.

```ts
const aj = arcjet({
  key: process.env.ARCJET_KEY!,
  rules: [],
  proxies: [
    "203.0.113.100", // A single IP
    "203.0.113.0/24", // A CIDR for the range
  ],
});
```

SDKs reject malformed proxy addresses and CIDRs. A trust-all range such as
`0.0.0.0/0` or `::/0` remains available for unusual deployments, but emits a
warning because it treats every connecting peer as a trusted proxy.

### Verify client IP selection

The SDKs expose the selection without sending a decision. Use this in staging
with representative requests from every ingress path:

| SDK | Debugging API |
| --- | --- |
| JavaScript | `client.clientIpDetails(request)` in `@arcjet/node`; `findIpDetails()` or `resolveClientIp()` from `@arcjet/ip` for other adapters |
| Python | `client.client_ip_details(request, ip_src=...)` |
| Go | `client.ClientIPDetails(request)` |

The result contains the selected IP, its provenance, whether the SDK tied the
source to the request path, and the header name when applicable. The same data
is logged at debug level as `client_ip_provenance`, `client_ip_verified`, and
`client_ip_header`. A `verified` value confirms how the SDK reached the source;
it does not prove that the surrounding network configuration is safe.

Expected production provenance is normally `platform`, `direct`,
`trusted-proxy`, or a deliberately supplied `manual` value. Investigate
`unverified-header`, confirm the application is reachable only through the
expected ingress, make that ingress overwrite or safely append forwarding
headers, and configure every trusted hop.

### Proxy services like Cloudflare

Some providers don't add themselves to `X-Forwarded-For`. Instead they pass the
real client IP in their own header – for example, Cloudflare uses
`CF-Connecting-IP`. For these you can pass a _proxy service_ in the `proxies`
option instead of a plain IP address.

The JavaScript SDKs export a `cloudflare()` helper for this. When a request
arrives from a known Cloudflare IP range, Arcjet reads the real client IP from
Cloudflare's header. This is only trusted when the connecting address is within
Cloudflare's verified IP ranges, so the header can't be spoofed by a direct
client.

<Code code={CloudflareTS} lang="ts" title="/lib/arcjet.ts" />

You can combine proxy services with plain IP addresses in the same list, such as
`proxies: ["203.0.113.0/24", cloudflare()]`.

:::caution[Cloudflare in front of Vercel is not recommended]
If you deploy to Vercel, Vercel
[recommends against putting Cloudflare (or any reverse proxy) in front of your
application](https://vercel.com/kb/guide/cloudflare-with-vercel). Doing so hides
traffic and can cause bot challenges to misfire as
proxy exit-node IPs rotate. Arcjet already auto-detects the proxy IPs for Vercel,
so you don't need to configure `proxies` on Vercel unless you've added another
proxy in front. If you do run Cloudflare in front of Vercel, add `cloudflare()`
to `proxies` so Arcjet still sees the real client IP.
:::

## Implement your own error handling

Calls to `protect()` don't throw an error. Arcjet is designed to fail open so
that a service issue or misconfiguration does not block all requests.

If there is an error condition when processing the rule, Arcjet returns an
`ERROR` result for that rule and you can check the error message on the rule's
error result for more information. For example:

<Tabs syncKey="language">
<TabItem label="JavaScript / TypeScript">

```ts
const decision = await aj.protect(req);

if (decision.isErrored()) {
  // Fail open: log the error and allow the request
  console.error("Arcjet error", decision.reason.message);
}
```

</TabItem>
<TabItem label="Python">

```py
decision = await aj.protect(request)

if decision.is_error():
    # Fail open: log the error and allow the request
    logger.error("Arcjet error: %s", decision.reason_v2.message)
```
