Arcjet splits processing between your environment and the Arcjet cloud. The SDK
analyzes what it can locally – a sandboxed WebAssembly module inspects request
details, and the request body doesn't leave your application. The Arcjet Cloud
API handles the work that local analysis can't do on its own: real-time
decisions, background analysis, and the activity that you review in the Arcjet
Console.

The [Arcjet privacy policy](https://arcjet.com/privacy) sets out the legal basis
for processing. This page describes what Arcjet processes, where, and for how
long.

## Where Arcjet processes data

The following table summarizes where each kind of data is processed:

| Data                                                                     | Where it's processed |
| ------------------------------------------------------------------------ | -------------------- |
| Request body                                                             | Your environment     |
| Local policy inputs                                                      | Your environment     |
| Request IP address, headers, custom characteristics, and email addresses | Arcjet cloud         |
| Text that you pass to prompt injection detection or content moderation   | Arcjet cloud         |
| Decision metadata and server policy inputs                               | Arcjet cloud         |
| Coding agent and other agent activity                                    | Arcjet cloud         |

Arcjet uses the data that it processes in the cloud for the following purposes:

- Make real-time decisions.
- Run background analysis and reporting.
- Show request and agent activity in the Console.

### Request protection

When you call `protect()`, the SDK sends the following request data to Arcjet:

- The IP address.
- The method, host, path, and query string.
- The headers.
- Any <Link.Page href="/fingerprints#custom-characteristics">custom characteristics</Link.Page> that you use for <Link.Page href="/fingerprints">fingerprints</Link.Page>.
- The email address, if you use <Link.Page href="/email-validation">email validation</Link.Page>.
- The text that you pass for <Link.Page href="/prompt-injection">prompt injection detection</Link.Page>, if you use it.

Everything else, including the request body, stays in your environment. For
example, <Link.Page href="/sensitive-info">sensitive information detection</Link.Page> on HTTP request bodies runs locally, so the body isn't sent to Arcjet.
The SDK reports the type and position of each finding, but not the matched
text.

### Guards and agents

When you call `guard()`, use a <Link.Page href="/coding-agents">coding agent</Link.Page>, or submit other agent
activity, Arcjet receives the values that it needs to evaluate your policies and
show the activity in the Console. These values can include the following:

- Decision metadata, such as the conclusion, the rules that fired, timings, and
  correlation identifiers.
- An actor identifier, when your application asserts one.
- Server policy inputs that you map for a Guard policy – for example a
  recipient address, a command, or the paths and domains in a tool call.
- The text that you pass to a
  <Link.Page href="/prompt-injection">prompt injection</Link.Page> or
  <Link.Page href="/content-moderation">content moderation</Link.Page> rule.
- Tool call details, prompts, and related session metadata from coding agents
  and other agent submissions.

Values that you mark as local policy inputs stay in your environment. Only
their declared kind and evaluation result leave the SDK.

## Data retention

Arcjet retains decision and activity records so that you can investigate
traffic and agent sessions in the Console, API, CLI, and MCP server. Depending
on the product, a record can include the following:

- Request and Guard decision outcomes, and the rules that contributed to them.
- Request metadata processed in the cloud, such as the IP address and headers.
- Server policy inputs and agent session details that were sent for a decision.

### What Arcjet stores by default

Arcjet doesn't store everything that it processes. By default, it handles the
text that you send for detection as follows:

- **Prompt injection text is stored** with the decision, so that you can
  investigate a detection. This covers the text that you pass to `protect()`
  and to a Guard prompt injection rule, and the server policy inputs that a
  prompt injection detector reads.
- **Content moderation text isn't stored.** Arcjet keeps the verdict and the
  billing count, but not the text.
- **Server policy inputs are stored**, except values that the server-side
  sensitive information detector flags. Arcjet removes a flagged value and keeps
  only the entity types and positions.
- **Sensitive information that the SDK detects** is recorded as entity types and
  positions only. The matched text stays in your environment.
- **Captures and agent activity are stored.** This includes SDK captures,
  coding agent hook events, OpenTelemetry exports, and Claude Compliance
  imports.

Arcjet redacts the values of authentication headers, such as `Authorization`,
before it stores a request.

To stop Arcjet from storing prompt injection text for your organization,
contact [support@arcjet.com](mailto:support@arcjet.com). To stop Arcjet from
storing customer content altogether, use
[zero data retention](#zero-data-retention).

### How long Arcjet stores data

How long Arcjet stores a record depends on its type:

| Record                                                                                          | Storage period |
| ----------------------------------------------------------------------------------------------- | -------------- |
| Request decisions from `protect()`, including prompt injection text                             | 30 days        |
| Request headers and query parameters                                                            | 3 days         |
| Guard decisions, including server policy inputs and prompt injection text                       | 90 days        |
| Captures and agent activity, including coding agent hooks, OpenTelemetry, and Claude Compliance | 90 days        |

Arcjet also keeps backups for disaster recovery, and a backup can retain data
for longer than the storage period.

Your plan's log retention sets how far back you can view records in the
Console, API, CLI, and MCP server, up to the storage period. For example, the
Individual plan shows the last hour and the Startup plan shows the last
24 hours. Enterprise plans can include custom retention. For each plan's
window, see [Arcjet pricing](https://arcjet.com/pricing). Arcjet keeps
aggregated data for longer, so that you can review traffic patterns over time.

## Zero data retention

For organizations that can't allow a vendor to store customer content, Arcjet
offers zero data retention (ZDR). To find out whether your organization is
eligible, contact [support@arcjet.com](mailto:support@arcjet.com).

With ZDR, Arcjet evaluates requests and agent activity on the full input, so
your protections work the same way. After it responds, Arcjet keeps only a
limited record of each decision, for debugging, performance, and billing.

### What Arcjet keeps

Depending on the product, each record contains only:

- Arcjet-issued identifiers for the site, decision, capture, and rule, and your
  site key.
- The time Arcjet received the request and where it processed it.
- The SDK and its version.
- The policy and rule IDs, the policy revision, and each rule's type and mode.
- The allow, deny, or error outcome, with a fixed reason code and error code.
- For coding agents: the hook event, the tool category (such as `shell` or
  `file_write`), the agent vendor, product, and surface, and the permission
  mode.
- Session flags, such as `prompt_injection`.
- Latency, and counts of requests, rules, and tokens.

Rate limit and Shield counters use hashed keys and expire with the rule's
window.

### What Arcjet doesn't keep

Arcjet doesn't keep request IP addresses, headers, paths, query parameters,
email addresses, prompts, tool arguments or results, transcripts, server policy
input values, rule labels or metadata, tool, MCP server, or model names, or
generated summaries. Because tool names aren't kept, activity can't be broken
down by individual tool.

Your own SDK capture event names are recorded as `other`. Claude Compliance
imports are recorded as the event type and time only.

Log exports that Arcjet sends for you contain the same limited records.

### Agent session data

Session analysis rules can use the minimum recent content that their decisions
need. Arcjet deletes each item when its session ends and, in any case, no later
than 24 hours after it processed the item. Pausing, retrying, or resuming a
session doesn't extend that deadline.

A session's flags stay active until a Console user clears them or 24 hours pass
with no activity from the agent. Ending the agent's session doesn't clear them.
After the content that set a flag is deleted, the session still shows which
policy, rule, and flag applied, but not the text that triggered it.

Arcjet reviews tool results for prompt injection in the background only when a
published policy uses the `prompt_injection` session flag.

### What zero data retention doesn't cover

Two kinds of data are kept as usual, because you supply them on purpose:

- **Discovery data from devices that you enroll.** If you deploy Arcjet
  Discovery, the AI apps, services, and devices that it reports are kept so that
  you can review them.
- **The reason that you enter when you clear a session flag.** Arcjet keeps it,
  with who cleared the flag, as the record of the decision. The Console shows a
  notice where you enter it.

### Debug a decision under zero data retention

After the content is deleted, Arcjet can show the policy, rule, outcome, and
reason code for a decision, but can't reconstruct the content. Where a field
wasn't kept, the Console, API, CLI, and MCP server say so rather than showing
an empty value. To keep a complete record of a decision, store the decision that
the SDK returns in your own systems.

Traffic that Arcjet processed before ZDR took effect for your organization
follows the previous storage periods, unless you ask
[support@arcjet.com](mailto:support@arcjet.com) to delete it.

## Geographic processing

Arcjet runs its API in multiple regions, across several platforms, to keep
response times low. Arcjet aims to process each request in the same region as
your application, but redundancy and failover can route a request to another
region.

If you need processing to stay in a specific region, regional processing
controls are part of the Enterprise plan. For more information, see
[Arcjet pricing](https://arcjet.com/pricing).
