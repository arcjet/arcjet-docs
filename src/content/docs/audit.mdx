A security review asks three questions about an agent action: what happened,
why was it allowed or denied, and can you prove it. Arcjet records the evidence
each guard decision needs to answer them by replay rather than by narration.

This page covers what Arcjet records, what it deliberately doesn't, and how to
reconstruct a decision. For recording actions your own application took, see
<Link.Page href="/guards/capture">Capture events</Link.Page>. For ingesting
activity from agents you don't instrument, see
<Link.Page href="/observe">Observe agent activity</Link.Page>.

## What Arcjet records for a decision

Every guard call produces a decision record. Alongside the conclusion and the
per-rule results, Arcjet records what the policy read:

| Recorded                 | What it is                                                                  |
| ------------------------ | ----------------------------------------------------------------------------- |
| Actor                    | The opaque principal your application asserted.                             |
| Declared `SERVER` inputs | Each validated input value, in a dedicated table with deterministic JSON.   |
| Detector verdicts        | The results the expression read, such as whether a detector matched.        |
| Policy revision          | The stored policy that was selected.                                        |
| Policy artifact digest   | A SHA-256 digest of the compiled program that actually evaluated.           |

Recording is best effort and never changes a decision. If Arcjet can't record
the evidence, the action is still allowed or denied on the policy's answer.

An expression rule records no input name. An expression reads whatever inputs
its body names, so there's no single input to attribute it to.

## What is never recorded

Three categories never reach Arcjet's storage, and each is a design constraint
rather than a setting:

- **Raw `LOCAL` input values.** A `LOCAL` value stays in SDK memory. Arcjet
  receives a domain-separated digest and the SDK's verified detector result.
  "A detector found a card number" is recorded; the number isn't.
- **Rego source and rule descriptions.** Both are author-written text, treated
  as untrusted. They're shown to their own author and excluded from logs,
  metrics, traces, and errors.
- **Raw actor and input values in telemetry.** They're recorded as evidence, in
  storage bound by retention, but never written to a log line or a metric.

A decision whose local rule denied and short-circuited records no detector
verdicts at all, because the expression never ran to read any. It also omits
the `SERVER` inputs, so a value the application mapped to both a local and a
server input still never arrives.

<Aside type="caution">
  A local-input digest is correlation data, not anonymization. A low-entropy or
  enumerable value can be guessed and hashed. `LOCAL` limits what's
  transmitted; it isn't a general privacy guarantee.
</Aside>

## Prove which policy ran

A policy revision names a database row. The artifact digest names the program
that evaluated. Both are recorded, because a row and a program are different
claims:

```json
{
  "policy_evaluation": {
    "policy_id": "gpol_01abc123",
    "policy_revision": 7,
    "artifact_sha256": "9f2a…",
    "status": "APPLIED"
  }
}
```

`artifact_sha256` is empty when no expression rule evaluated. A policy decided
entirely by detectors compiles to no artifact.

To reconstruct a decision:

1. Fetch the snapshot for the revision the decision names.
2. Recompute the artifact digest from the snapshot and confirm it matches the
   digest on the decision.
3. Re-evaluate the recorded `SERVER` inputs and detector verdicts against that
   artifact.

The evaluator is deterministic and the artifact is immutable, so the replay
returns the same answer the original call did. That's what makes the record
evidence rather than a summary: nothing about the decision depends on a clock,
a network call, or a model, because the policy language has access to none of
them.

Recording the detector verdicts alongside the inputs is what makes this work
for a policy with a `detected` condition. With only the values, the artifact
and the inputs would both be preserved and the answer would still differ.

## Who changed a policy

Every policy write records the Arcjet user, the identity provider's user and
session, whether the session was impersonated, and the impersonator's address.
This is stored on both the current policy and its immutable revision snapshot,
rather than resolved from the session later, so the record still answers "who
made this change" long after the session itself has expired.

Each revision snapshot also records the compiler and profile versions that
produced its bundle, so the versions travel with the bytes a rollback would
republish.

## Retention

| Record                    | Retained   |
| ------------------------- | ---------- |
| Decisions, rules, actors, and inputs | 90 days |
| Capture events            | 90 days    |
| Policy revision snapshots | 10 years   |

Revision snapshots outlive the decisions that cite them on purpose. A snapshot
deleted while a decision still referenced it would delete the answer to "why
was this denied?" while the question was still being asked. Snapshots survive
site deletion for the same reason.

## Telemetry for operating a policy

Arcjet's own decision logs carry the fields you need to watch a policy in
production, including which rules denied and what the expression cost against
its evaluation budgets. A dry-run rule reports separately from a live one, so a
rule that would have denied is visible per rule before you promote it.

Rule and policy IDs are safe to record because the compiler bounds and
character-restricts them. Rule descriptions, policy source, and every input
value are excluded.

## Where evidence is stored

Arcjet stores decision evidence in its cloud by default. Single-tenant and
private VPC deployments are available, and you can also send the record to
storage you manage. For deployment options, contact
[sales@arcjet.com](mailto:sales@arcjet.com).

Some controls never produce evidence outside your environment at all.
Sensitive-information detection runs in your process, so its findings are
recorded as verdicts and the text it read is never transmitted.
